PART 1 - CONTEXT

Hello, today we are going to work on a task based on a Data Engineering challenge.
We are going to split this video into three parts: first the context of the challenge and the solution, then finding the first issue, and finally applying the solution.

So, let's begin with the context.
The challenge asks us to read three different source files and store them in tables in any database engine. All ingestion must be idempotent, and it must store clean, quality data.
The solution uses Cursor, Docker, Flask, Spark and MySQL. It is split into two Docker containers: one runs MySQL, the other runs the Flask app with Spark. The Flask app exposes endpoints, and we send POST requests to start each ingestion. Today we only focus on hired_employees.

[ACTION: Click the Explorer icon at the top of the left activity bar. Expand the db folder and click init.sql.]
Here we see all the DDL. For hired_employees there are two tables: hired_employees_historical keeps the raw data, and hired_employees holds the final data. So the process first appends the raw data to the historical table, then transforms and deduplicates it into the final table. That is a good way to keep the pipeline idempotent.

[ACTION: Expand the app folder and click main.py. Scroll with the mouse wheel down to silver_employees, around line 185.]
In silver_employees, the code creates a temp table, applies a window function to keep one record per id, and then upserts into hired_employees.

The historical table has every row from the file, but the final table has fewer. Those rows disappeared with no trace. The current code filters out rows with null id, department_id or job_id, and removes duplicate ids, without recording why. Also, silver_employees catches exceptions and returns the error as a string, so the endpoint can still answer as a success.
So the first issue is that we lose data silently and cannot audit it.


PART 3 - APPLYING THE SOLUTION

The solution has three parts. First, a new table, hired_employees_rejected, stores every discarded row with its reason. Second, each row gets a reject_reason: missing id, department_id, job_id or datetime, or duplicate_id for extra copies of an id. Third, we reconcile the counts: rows read must equal rows loaded plus rows rejected, or the job fails.

def silver_employees(df_last_updated):
    temp_table = 'temp_employees'

    # 1) Motivo de rechazo por fila (null = fila valida).
    #    Si una fila tiene varios problemas, queda el primero de la cadena.
    #    Ojo: con el modo PERMISSIVE, un valor que Spark no puede parsear (ej: "abc" en job_id)
    #    tambien llega como null, asi que "missing" significa vacio o invalido.
    df = df_last_updated.withColumn(
        "reject_reason",
        when(col("id").isNull(), "missing_id")
        .when(col("department_id").isNull(), "missing_department_id")
        .when(col("job_id").isNull(), "missing_job_id")
        .when(col("datetime").isNull(), "missing_datetime")  # regla nueva: borrala si solo queres registrar lo que ya se descartaba
    )

    # 2) Ids duplicados dentro del mismo archivo: queda la primera fila valida, el resto se rechaza.
    #    asc_nulls_first ordena primero las filas sin motivo (las validas) dentro de cada id.
    window_spec = Window.partitionBy("id").orderBy(col("reject_reason").asc_nulls_first(), col("load_timestamp"))
    df = df.withColumn("row_number", row_number().over(window_spec)) \
        .withColumn("reject_reason",
                    when(col("reject_reason").isNull() & (col("row_number") > 1), lit("duplicate_id"))
                    .otherwise(col("reject_reason"))) \
        .drop("row_number") \
        .cache()
    # cache: el df se usa en varios conteos y escrituras. Sin cache Spark lo recalcula en cada una y,
    # como la window empata en load_timestamp, un duplicado podria quedar cargado Y rechazado.

    df_valid = df.filter(col("reject_reason").isNull()) \
        .select("id", "name", "datetime", "department_id", "job_id", "load_timestamp")
    df_rejected = df.filter(col("reject_reason").isNotNull()) \
        .select("id", "name", "datetime", "department_id", "job_id", "reject_reason", "load_timestamp")

    # 3) Reconciliacion: todo lo que entra sale cargado o rechazado
    rows_read = df.count()
    rows_loaded = df_valid.count()
    rows_rejected = df_rejected.count()
    if rows_read != rows_loaded + rows_rejected:
        raise ValueError(f"Reconciliacion fallida: leidas={rows_read} cargadas={rows_loaded} rechazadas={rows_rejected}")
    rejected_by_reason = {row["reject_reason"]: row["count"]
                          for row in df_rejected.groupBy("reject_reason").count().collect()}

    # 4) Rechazadas con su motivo. Append: cada carga suma sus rechazos y se distinguen por load_timestamp
    df_rejected.write \
        .format("jdbc") \
        .options(**JDBC_OPTIONS) \
        .option("dbtable", "hired_employees_rejected") \
        .mode("append") \
        .save()

    # 5) Validas: igual que antes, tabla temporal + UPSERT
    df_valid.write \
        .format("jdbc") \
        .options(**JDBC_OPTIONS) \
        .option("dbtable", temp_table) \
        .mode("overwrite") \
        .save()

    connection = pymysql.connect(**mysql_config)
    cursor = connection.cursor()

    # Si el id es nuevo, lo inserta; si ya existe, lo actualiza con el ultimo dato.
    merge_query = f"""
        INSERT INTO hired_employees
        SELECT * FROM {temp_table}
        ON DUPLICATE KEY UPDATE
            name = VALUES(name),
            department_id = VALUES(department_id),
            job_id = VALUES(job_id),
            load_timestamp = VALUES(load_timestamp)
    """
    cursor.execute(merge_query)
    connection.commit()

    cursor.execute(f"DROP TABLE IF EXISTS {temp_table}")
    connection.commit()
    cursor.close()
    connection.close()

    df.unpersist()

    return {
        "rows_read": rows_read,
        "rows_loaded": rows_loaded,
        "rows_rejected": rows_rejected,
        "rejected_by_reason": rejected_by_reason,
    }
